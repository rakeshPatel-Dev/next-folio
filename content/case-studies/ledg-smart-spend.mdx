## Project Overview

Ledg is a personal finance application built around a simple idea: tracking
money should not require users to fight through a complicated finance
interface.

The application allows users to record income and expenses, organize their
financial activity into different spaces, monitor spending patterns, and keep
lending and borrowing separate from normal income and expense calculations.

Spaces can represent different contexts such as:

- Personal
- Family
- Trip
- Business

This allows users to keep different financial contexts organized without
requiring completely separate accounts or applications.

---

## The Problem

Many personal finance applications become difficult to use because recording
a simple transaction requires too many steps, while the analytics often focus
on displaying numbers rather than helping users understand them.

Ledg was designed around several practical problems:

- Recording everyday transactions should be quick
- Different financial contexts should remain separated
- Lending and borrowing should not be treated as normal spending
- Users should be able to understand where their money is going
- Financial summaries should be calculated efficiently on the server
- The interface should remain simple despite supporting multiple financial
  workflows

The goal was to build something that could remain simple for everyday use
while still having a solid technical foundation underneath.

---

## Goals

The primary goals were to:

- Make transaction tracking quick and straightforward
- Organize finances through flexible spaces
- Separate lending and borrowing from normal spending
- Provide useful financial analytics
- Keep calculations on the server where appropriate
- Build a secure authentication system
- Keep the data model lean and avoid unnecessary abstractions
- Create a foundation for future voice-based transaction entry and AI-powered

### Transaction Management

Transactions are the core financial record in Ledg.

Users can record:

- Income
- Expenses

Each transaction can contain:

- Amount
- Category
- Note
- Date
- Tags
- Payment method
- Space

Transactions support server-side filtering and pagination rather than

Supported payment methods include:

- Cash
- Card
- Bank Transfer
- Wallet

The transaction interface is designed around quick entry, with optimistic UI

### Lending & Borrowing

Lending and borrowing are treated separately from normal income and expense
tracking.

This distinction is important because giving someone money is not the same
as spending money, and receiving a repayment is not the same as earning
income.

Ledg's dues model is designed around the actual movement of money while
keeping the financial meaning of the event separate.

A lending or borrowing record can track:

- Person
- Amount
- Date
- Optional due date
- Settled amount
- Status
- Related transaction information

This allows the application to represent outstanding money without
distorting spending and income analytics.

<Callout variant="note" title="Why this matters">
  A loan should not automatically appear as an expense, and a repayment
  should not automatically appear as income. Keeping the dues domain separate
  makes financial analytics more accurate.
</Callout>

## Performance Architecture

One of the more important engineering problems in Ledg was the dashboard
data flow.

An early approach required fetching transactions separately for each space
and then aggregating the results on the client.

That created an unnecessary request pattern:

1. Authenticate the user
2. Fetch spaces
3. Fetch transactions for each space
4. Transfer unnecessary transaction data
5. Aggregate the data in the browser

This effectively created an N+1 request pattern for the dashboard.

The architecture was changed to use server-side aggregation and a dedicated
dashboard summary endpoint.

Instead of returning large collections of transactions, the API returns only
the information required by the dashboard.

This reduces:

- Number of network requests
- Amount of transferred data
- Client-side computation
- Dashboard rendering work

Redux Toolkit Query is then used for caching and request lifecycle
management on the client.

<Callout variant="note" title="Architecture principle">
  Fixing the API shape and query strategy comes before adding another caching
  layer. Redis is not used simply to compensate for inefficient queries or
  unnecessary API requests.
</Callout>

## Data Architecture

Ledg intentionally keeps its application data model relatively small.

Better Auth handles authentication-related data, while Ledg focuses on the
financial domain.

The main application concepts are:

- Spaces
- Transactions
- Dues / debt records

The application does not introduce separate models for concepts that can be
represented directly by transactions.

For example, categories and payment methods are represented as controlled
values rather than requiring additional database collections.

This keeps the data model easier to reason about while leaving room for
future expansion if user-defined categories or more complex financial
accounts become necessary.

## Key Design Decisions

### 1. Spaces Instead of Separate Financial Accounts

The goal was to let users organize financial contexts without introducing
unnecessary account-management complexity.

A user can create Personal, Family, Trip, or Business spaces while still
having one identity and one application.

### 2. Server-Side Financial Aggregation

Financial calculations are performed through MongoDB aggregation pipelines
rather than downloading large transaction sets and calculating everything in
the browser.

This makes the API more useful for dashboards and analytics while reducing
client-side work.

### 3. Dues as a Separate Domain

Lending and borrowing are not treated as ordinary income or expenses.

Separating the dues domain prevents loans and repayments from distorting
spending and income statistics.

### 4. Lean Data Model

Ledg avoids creating database models simply because a concept exists in the
UI.

Categories and payment methods are controlled values, while authentication
data remains under Better Auth.

This keeps the application's own database focused on the actual financial
domain.

### 5. RTK Query for Server State

Redux Toolkit Query handles API caching, request lifecycle management, and
client-side synchronization.

This avoids manually managing loading, caching, invalidation, and optimistic
updates across every feature.

## What I Learned

Ledg taught me that a finance application is less about displaying numbers
and more about deciding what those numbers actually mean.

One of the most important decisions was separating lending and borrowing from
income and expenses. Treating every movement of money as either an expense or
income would produce misleading analytics.

I also learned the importance of designing API responses around the actual
screen consuming them.

The dashboard initially had a data-fetching pattern that pushed too much
work to the client. Moving aggregation to the backend made the architecture
cleaner and created a much better foundation for analytics.

Another important lesson was avoiding unnecessary abstractions. A finance
application can quickly accumulate models for accounts, categories,
payment methods, and other concepts. Ledg deliberately keeps those concepts
simple until the product actually needs more complexity.

## Future Direction

Ledg is being designed with several future capabilities in mind.

### Voice Transaction Entry

The planned voice workflow allows users to say something such as:

> "I bought a samosa for 300."

The system can extract structured transaction information and pass it through
the same validation and transaction APIs used by the normal interface.

The AI layer would interpret the input, while the existing application API
would remain responsible for validation and database changes.

### AI Financial Analysis

A future AI layer can analyze deterministic financial data and provide
higher-level observations such as:

- Spending increases
- Category changes
- Frequent small purchases
- Recurring spending patterns
- Month-end spending behavior
- Changes in savings rate

The intention is for AI to interpret financial data rather than replace the
underlying calculations.
