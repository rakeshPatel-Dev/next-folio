## Project Overview

Academix is a full-stack academic management system built to bring common academic administration tasks into one platform.

The system gives **Admins, Teachers, and Students** their own experience, with role-based access deciding what each person can see and do.

Admins manage students, teachers, and courses, assign teachers to courses, and enroll students. Teachers get access to their assigned courses and the student information that comes with them. Students can view their enrolled courses and academic details.

I wanted this to go past basic CRUD, so it also includes authentication, authorization, email services, dashboard analytics, and a structured REST API.

---

## The Problem

Academic information usually ends up spread across spreadsheets, paper records, or a handful of disconnected tools.

Simple things like managing students, assigning teachers to courses, and tracking enrollments end up being far more manual than they should be.

The goal was to build one place where admins, teachers, and students could each access what matters to them without jumping between tools.

---

## Goals

## Key Features

### Role-Based Authentication

Academix has three primary roles:

- **Admin**
- **Teacher**
- **Student**

Whenever someone tries a protected action, the system checks who they are and what their role allows before moving forward:

| Role | Can manage students | Can assign teachers | Can manage courses |
| --- | :---: | :---: | :---: |
| **Admin** | Yes | Yes | Yes |
| **Teacher** | No | No | Assigned only |
| **Student** | No | No | No |

<Callout variant="note">
  Authorization runs as middleware, so protected routes don't repeat
  access-control logic. They just declare which roles are allowed.
</Callout>

Authentication uses **JWT**, and passwords are hashed with **bcrypt**.

Protected routes block unauthenticated users, and authorization logic makes sure each user only does what their role permits.

## Technical Architecture

Academix splits the frontend and backend. The React app talks to an Express REST API over Axios, and the backend routes each request through authentication, authorization, controllers, services, and finally Mongoose and MongoDB.

### Layer Responsibilities

- **React App** handles UI, routing, forms, charts, and API calls.
- **Express API** handles the HTTP layer, routes, and request handling.
- **Auth Middleware** verifies identity and enforces role-based access.
- **Controllers** handle request/response and hand off to services.
- **Services** hold business logic and the email service.
- **Mongoose** handles schemas, validation, relationships, and queries.
- **MongoDB** is the persistence layer.

## Key Technical Decisions

### JWT-Based Authentication

I used JWT for stateless authentication between the frontend and the REST API.

Authentication and authorization run through middleware, so protected routes don't duplicate access-control logic.

---

### Role-Based Authorization

Instead of treating every authenticated user the same, Academix checks the user's role before letting them into protected operations.

That gives a clean permission boundary between **Admin**, **Teacher**, and **Student**.

---

### Service Layer

Business logic lives in services, separate from HTTP-specific controller logic.

Instead of stuffing every operation into controllers, requests flow through a clear chain:

<FlowSteps steps={["Route", "Controller", "Service", "Model"]} />

This keeps the backend easier to maintain as features grow.

---

### Dedicated Email Service

Email lives in its own service rather than being wired directly into individual controllers.

That way different parts of the app can reuse the same email setup.

---

### MongoDB with Mongoose

MongoDB handles persistence, and Mongoose takes care of:

- Schema definitions
- Data modeling
- Validation
- Relationships
- Database queries

## Challenges & Solutions

### Managing Different User Roles

Different users need different permissions and interfaces.

**Solution:** Authentication and authorization middleware splits identity verification from role-based access control.

---

### Keeping Controllers Maintainable

As features piled up, putting database queries and business logic directly into controllers would have made them harder to maintain over time.

**Solution:** Business logic moved into service modules, so controllers stay focused on requests and responses.

---

### Managing Academic Relationships

Students, teachers, and courses are all related, which makes the data model more involved than standalone CRUD resources.

**Solution:** Mongoose relationships connect the academic entities and support things like course assignment and student enrollment.

---

### Handling Email Logic

Sending emails from controllers would have tightly coupled notification logic with individual operations.

**Solution:** A dedicated email service handles delivery through Nodemailer.

---

## Security

Academix includes a few basic security measures:

- Password hashing with bcrypt
- JWT-based authentication
- Protected API routes
- Role-based authorization
- Environment variables for sensitive config
- CORS configuration
- Server-side request validation

<Callout variant="warning" title="Before production">
  Enable secure cookies over HTTPS, rotate the JWT secret via environment
  variables, and rate-limit the auth endpoints to guard against credential
  stuffing.
</Callout>

Sensitive values like database URLs, JWT secrets, and SMTP credentials stay outside the source code through environment variables.

## Lessons Learned

### CRUD Is Only the Starting Point

Basic CRUD was the easy part. The more interesting problems came from connecting those resources and enforcing who could access or change them.

### Authorization Is Different From Authentication

Checking that a user is logged in is only half of access control. The other half is deciding what that user is allowed to do.

### Separation of Concerns Matters

Splitting controllers, services, middleware, and email logic makes the backend easier to reason about and extend.

### Data Relationships Shape the Application

Students, teachers, and courses can't be treated as fully independent resources. Their relationships drive both the database design and the user experience.

### Real Systems Need More Than a UI

Building Academix pushed me past just building interfaces and CRUD operations into thinking about authentication, authorization, data flow, service boundaries, and maintainability.

## What I'd Improve

If I kept working on Academix, the next improvements would focus on useful academic workflows rather than adding complexity for the sake of it:

- Add attendance management for individual courses
- Add assignment creation and student submissions
- Add search, filtering, and pagination to larger datasets
- Add a secure password-reset flow through the existing email service
- Add activity logs for important admin actions
- Improve dashboard analytics as more academic data shows up
- Add automated backend and frontend tests

The goal would be to gradually turn Academix from an academic management system into a fuller **learning management platform**, while keeping the architecture simple and maintainable.
